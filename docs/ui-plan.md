## 2. Goal

Let a developer do this in any Benos project:

```sh
benos init
benos add button input dialog
```

and get production-quality, accessible, themeable components whose source code is copied into their project, so they own and can edit it. The UI system is **designed together with Benos but fully optional**: a developer who never runs `benos add` pays nothing.

The developer experience should feel like shadcn/ui, built natively for Benos's fine-grained reactivity, run-once components, and typed props.

---

## 3. Architecture

Three layers:

1. **`@benosjs/primitives`** (published npm package, runtime dependency): unstyled, accessible behavior (state, keyboard interaction, focus management, ARIA attributes) for complex components. Built on **Zag.js** state machines with a Benos adapter, not written from scratch. Accessibility behavior is hard to get right; reuse proven work.
2. **The `benos` CLI** (published npm package): `init`, `add`, `list`, `diff`, `update`. It copies component source from the registry into the user's project.
3. **The component registry**: versioned component source and metadata (files, dependencies on primitives and other components, CSS, tokens). Styled components are thin, readable layers over primitives.

Theming uses **CSS custom properties (design tokens)** for color, spacing, radius, typography, shadows, and motion, with light and dark modes. The default visual style must match the Benos brand and logo in `assets/brand/`.

### Starting decisions (confirm or challenge in the design phase)

- **Styling:** plain CSS with CSS variables, one stylesheet per component, with no Tailwind requirement. A Tailwind preset can come later. Justify the final choice.
- **CLI package name:** use the unscoped `benos` package if available on npm, so users can run `npx benos add button`; otherwise `@benosjs/cli` exposing a `benos` binary. Check availability; do not publish anything to reserve it.
- **Registry format:** compatible with shadcn's registry schema where practical, rather than inventing a proprietary format.
- **Registry hosting:** registry JSON served from the GitHub repository (or the Benos website) at versioned URLs, so `benos add` works without a custom server.
- **Updates:** `benos diff` shows local versus registry changes; `benos update` performs a three-way merge using the originally installed version as the base, never silently overwriting user edits.
- **Configuration:** `benos init` writes a small `benos.json` (component directory, CSS location, import alias) and installs the token stylesheet.

## 4. Initial Component Set

Build in batches, simplest first:

- **Batch 1 (no primitives needed):** button, input, textarea, label, card, badge, separator
- **Batch 2 (primitives):** checkbox, switch, radio group, select, tabs, accordion
- **Batch 3 (overlays):** dialog, popover, tooltip, dropdown menu, toast
- **Batch 4:** table (sortable, built for large lists using `<For>`)

Every component must:

- Use Benos idioms correctly: getter-backed props (no destructuring), `splitProps`/`mergeProps`, accessor callbacks, callback refs.
- Be fully typed, with type-level tests.
- Pass automated accessibility checks (axe-core) and keyboard tests in Chromium, Firefox, and WebKit.
- Support RTL and both color modes.
- Stay small and readable, since users will edit it.

---

## 5. Out of Scope

- **Blocks** (`benos add login`, `benos add dashboard`). These depend on the future forms and router modules and come later.
- Forms integration, validation, or data fetching inside components.
- A visual theme editor or design-tool integrations.
- Changes to `@benosjs/core` or `@benosjs/dom` semantics. Approved exception: add the public, no-argument `createUniqueId(): string` API to core for Zag IDs, with the existing 4,096-byte core and 10,240-byte core+DOM budgets unchanged. Future SSR derives IDs from request/root namespace, owner path, and per-owner call ordinal behind that signature. If another capability is missing, stop and raise it instead of working around it.

**Approved U4 accessibility requirements:**

1. The styled Switch component must expose `role="switch"` so assistive technology announces it as a switch. Verify this with axe-core and an accessibility-tree assertion.
2. Before implementing styled Select and Dropdown Menu, check Zag 1.44.0 for an option or documented integration pattern that closes the popup and moves focus on Tab according to the WAI-ARIA patterns. Use the supported pattern if present. If this is a Zag bug, draft an upstream issue with a minimal reproduction in `docs/upstream/` for the user to file; do not silently patch around Zag.
3. Confirm whether WebKit's Popover Tab result comes from its default keyboard-accessibility setting that skips buttons and links. If confirmed, configure the WebKit tests to match a keyboard user's full-access settings and retain regression coverage.
4. Determine whether WebKit's RTL radio ArrowLeft result is a Zag direction-handling issue or a WebKit quirk. If Zag is responsible, draft an upstream issue with a minimal reproduction in `docs/upstream/` for the user to file.

**U4 preflight findings (investigation only; no U4 implementation):**

- Zag 1.44.0 exposes no Select/Menu `closeOnTab` option or documented Tab integration hook. `closeOnSelect` concerns item activation only. Both connectors call `isValidTabEvent` and prevent the Tab key when the popup's only/last tabbable element is active. The WAI-ARIA APG select-only combobox example specifies committing the active value, closing, and allowing default Tab focus movement; the menu pattern specifies moving focus out and closing all menus. Draft reports for Zag are in [Select Tab behavior](upstream/zag-select-tab.md) and [Menu Tab behavior](upstream/zag-menu-tab.md). U4 must track these upstream; do not add a local key interception workaround without review.
- A Playwright WebKit probe skips a native button and link during sequential Tab navigation when starting from an input. Setting `AppleKeyboardUIMode=2` is retained for macOS test runs, but Playwright's WebKit browser did not honor that global setting in this run. The traversal fixture therefore gives its link `tabindex="0"`, which explicitly includes it in the keyboard sequence and keeps the cross-browser order assertion deterministic; the test does not claim to emulate Safari's system-wide Full Keyboard Access setting. See [WebKit bug 199671](https://bugs.webkit.org/show_bug.cgi?id=199671) and [Playwright issue 41808](https://github.com/microsoft/playwright/issues/41808). Verify equivalent behavior on non-macOS CI runners.
- The RTL RadioGroup ArrowLeft result reproduces with plain native radio inputs under `dir="rtl"`: Chromium and Firefox move to the second radio; WebKit keeps focus/selection on the first. Zag 1.44.0's radio connector does not handle arrow keys; it exposes native `input[type=radio]` controls and forwards `dir`. This is a WebKit native-radio behavior, not a Zag direction bug, so no Zag issue draft is needed. U4 should retain a browser-specific regression assertion and record the native behavior.
