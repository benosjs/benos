You are the lead architect for the next Benos track (`@benosjs/*`, currently v0.6.0): **streaming server rendering**. A server-rendered page starts with the shell and its Suspense fallbacks, each boundary's content follows as its opted-in data settles, and the browser hydrates progressively, claiming streamed content as it arrives. The track also pays down the server render cost that 0.6.0 measured at 35–45× Solid.

Build in phases with review checkpoints: design first, then implementation, with tests at every step. Push back when an idea is technically weak.

## 2. Context You Must Read First

- `docs/architecture/ssr.md`: the 0.6.0 contract. Marker grammar v1 and payload format v1 are frozen; the section "Kept open for streaming" states what this track builds on: markers nest by structure, every boundary is a slot pair with a stage ordinal, the payload is per root, and the server host serializes a finished tree that a streaming host can instead serialize eagerly.
- `docs/ssr-findings.md`: the measurements. Server render is 35–45× Solid (9.1 ms vs 0.22 ms for a 1,000-row table) because every dynamic position creates an owner, a slot, an effect, and marker nodes, and 29% of a large render is garbage collection. The recommended fix, a server fast path that evaluates bindings once when no boundary is pending, is this track's S2.
- `packages/server/src/{render,host,nodes,serialize}.ts`: the renderer settles in rounds (`await` tracked promises, flush, repeat), the host builds a request-local node tree, and `serialize.ts` writes it once.
- `packages/dom/src/hydrate.ts` and the claim seams in `packages/dom/src/index.ts`: the claim cursor, slot-scoped recovery, the `hold()` of a content stage whose reveal finds pending tokens, and the stage-ordinal check `<!--b:N-->`.
- `packages/async/src/index.ts`: `resource` under a server root (permanent token, `track`, record) and under a hydrating root (snapshot seeding); `Suspense` over the internal host.
- `docs/architecture/async.md`, `query.md`, `router.md`: request-local caches and how the router's initial navigation is tracked.
- `examples/dashboard`: the 0.6.0 server-rendered app (`entry-server.tsx`, `scripts/serve.mjs`).

### Decisions taken at S0

1. **Scope:** streaming plus the server fast path. Marker grammar v1 stays frozen; a shorter dynamic-text marker is not part of this track.
2. **Shell timing:** the response starts after the router settles (initial navigation and loaders), so `status` and `headers` are correct; the shell then waits for nothing behind a Suspense boundary.
3. **Hydration:** progressive, per boundary. `hydrate` runs as soon as its script executes; streamed content is claimed, not re-created.
4. **Delivery:** one inline script per patch, with an optional `nonce` for CSP.
5. **Fast path:** untracked unless pending. A binding runs once with no effect unless it read a pending resource or query, in which case it takes today's effect path. Components still run once on the server. Development warns on a write to a signal that a once-evaluated binding read.
6. **Boundary addressing:** the pending stage's opening marker becomes `<!--b:0:ID-->`, on streamed boundaries only. The 0.6.0 reader (`isOpen` and `Number(data.slice(2))` in `hydrate.ts`) must learn to read the ordinal up to the second colon; that is a reader extension, not a page change, so the protocol version stays 1 and every 0.6.0 page remains valid. S1 specifies it and counts its bytes.

### Constraints carried over

1. **Components run once.** Progressive hydration recreates owners by claiming; it never reruns setup on the client, and streaming adds no delay to writes after hydration.
2. **Opt-in serialization only.** A boundary is streamed only when it waits on a resource or query with an `ssr` codec. A boundary without one renders its fallback in the shell and loads on the client, as in 0.6.0. Private fields never reach HTML.
3. **Request isolation.** One root, ID namespace, resource registry, query cache, and abort signal per request. Aborting the signal ends the stream after the current chunk, disposes the root, and leaves pending boundaries to the client.
4. **Safe output.** Patch templates use the server's escaping; payload scripts and the runtime call escape `<`, `&`, and script-closing sequences; the runtime never evaluates application data. Error details go to server logs, not HTML.
5. **No hidden behavior.** No event replay before hydration and no fetching beyond what setup and loaders start.

## 3. Goals for the Streaming track

### `@benosjs/server`

- `renderToStream(app, options)` returning a promise that resolves, once the router has settled, to `{ status, headers, stream, done }`: `stream` is a `ReadableStream<Uint8Array>` of the app's HTML (shell, then patches); `done` settles when the last boundary is flushed or the request aborts. Options are those of `renderToString` plus `nonce`. The caller splits its HTML template around the host element and pipes the stream between the halves; the dashboard documents the pattern.
- **Stream protocol:** the shell is the 0.6.0 output with every streamed boundary rendered as its fallback, marked `<!--b:0:ID-->`. Each settled boundary sends one patch: a `<template>` holding the content stage (`<!--b:1-->…<!--/b-->`), a payload script with only that boundary's new snapshots (same format, `data-benos="ROOTID"`), and an inline script calling a runtime defined once in the first patch, which swaps the fallback range for the content and notifies hydration. An aborted or failed boundary sends an end notice so the client falls back to fetching.
- **The invariant:** after the last patch applies, the document equals what `renderToString` produces for the same state, byte for byte in the marked ranges. A page that finishes streaming before hydration hydrates through the existing code unchanged.
- **Server fast path (S2):** bindings outside pending data run once with no owner, effect, or subscription; the host serializes eagerly where no boundary is pending. Measured against Solid in `bench:ssr`; the honest ratio is reported whatever it is.

### `@benosjs/dom/hydrate`

- Progressive hydration: the runtime hands arriving patches and payload scripts to a live `hydrate`; a boundary whose patch has not arrived shows the claimed fallback; when content arrives the boundary reveals its content stage with the claim cursor active on the patched range. Any failure falls into the existing slot-scoped recovery.
- The end-of-stream notice turns every still-waiting boundary into a client fetch.

### `@benosjs/async`

- Under a hydrating root on a streamed page, a resource or query with an `ssr` codec whose snapshot is absent but whose boundary is marked pending **waits for the patch** instead of fetching, through a pending map on the request record. `@benosjs/query` reuses the same seam.

### Tooling and validation

- The dashboard streams, with one deliberately slow opted-in query behind a Suspense boundary, served on Node and Bun; the client build hydrates progressively.
- Measurements: time to first byte and time to the settled page for streamed versus `renderToString`; server render time against Solid after the fast path; hydration cost of a streamed page against a client render, on three engines.

### Not in this track

A shorter dynamic-text marker (protocol v2), script-less patch delivery, event replay before hydration, server components and server actions, `<head>` management, a `create-benos --ssr` template, and out-of-order streaming of anything other than Suspense boundaries (the router's loaders stay before the shell).

### S4 — Progressive hydration

The pending map, waiting resources and queries, runtime-to-hydrate handoff, claim-cursor reactivation on a patched range, and end-notice fallback. Tests in Chromium, Firefox, and WebKit: hydrate before any patch, between patches, and after all patches give the same DOM and zero mismatches; no client fetch for a streamed boundary; the end notice triggers exactly one fetch per unresolved boundary; input typed into the shell before hydration is preserved; a patch for an already recovered boundary is ignored; no leaked owners or listeners.
