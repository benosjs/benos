# Benos Phase 7 — Row creation at Solid's level

Phase 7 of [plan.md](./plan.md). **Status (2026-11-07):** complete. Verified at [RP-7d](./checkpoints/rp-7d.md), merged in benosjs/benos#32, and shipped in 0.7.2 (published 2026-11-09) with the three fixes it found (benosjs/benos#33, #34, and #35). The 0.3.0 performance track ([perf-plan.md](./perf-plan.md)) took row creation from about 1.6× to about 1.4× Solid with compiled direct output and lazy owners. This track goes after the remaining gap: creating, replacing, and clearing many rows, and the sortable table's first mount. Updates are already at or near Solid and must not regress.

Work in steps with review checkpoints: measure first, design second, implement in small measured increments, keep only changes that demonstrably help.

## 3. Constraints

- **Server rendering and hydration.** The server output, its markers, and the hydration claim stay byte for byte; the SSR, streaming, and hydration suites (Node and three browsers) are the proof. Client and server outputs keep coming from one compiler analysis.
- **Optimization parity.** `optimization: 'none'` and `'safe'` behave identically; every compiler fixture passes in both modes.
- **Development and production parity.** Production behaves as development minus diagnostics. Development diagnostics (duplicate keys, computations outside an owner, and the rest) keep firing.
- **Ownership, scheduling, and errors.** The semantics in `reactivity.md`, `scheduling.md`, and `ownership.md` are unchanged: cleanup order, disposal, error routing, and context lookup.

### Size caps

Production sizes at the start (minified + gzip): core 4,490 / 4,608; core + DOM 11,515 / 11,520; hydrate 3,962 / 4,096; server 7,688 / 8,448. At RP-7b the core + DOM cap was raised to **12,032 B** for this track (the user's words: "Approve, raise cap"); every change still reports its bytes beside its measured gain. A cap increase may be **proposed** with the exact byte cost of each change, its measured gain, and the alternative considered; the decision is the user's. Application bundle size (dashboard and gallery builds) is measured too, since generated code per template can grow while the runtime shrinks.

## 5. Hypotheses to test (not conclusions)

- **Settled bindings keep reactive state.** A binding whose first run read no signal still allocates an effect node and stays linked to its owner.
- **Owner per row.** Rows allocate an owner even when they register no cleanup or context.
- **Slot location.** Compiled slots are located through intermediate arrays or tuples instead of direct `firstChild`/`nextSibling` walks.
- **Event records.** Delegated handlers carry per-row records beyond the handler itself.
- **Disposal.** Clear and replace dispose rows one by one, unlinking each node, instead of in a batch with a range removal.
- **Garbage collection.** Short-lived arrays and closures during creation push work into the collector.
