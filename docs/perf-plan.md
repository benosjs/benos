## 2. The Problem

Current measurements (see `benchmarks/README.md`):

| Workload                                     | Benos vs Solid                                                                                                   |
| -------------------------------------------- | ---------------------------------------------------------------------------------------------------------------- |
| Create 1,000 rows                            | ~1.6×                                                                                                            |
| Replace 1,000 rows                           | ~1.6×                                                                                                            |
| Create 10,000 rows                           | ~1.5×                                                                                                            |
| Append 1,000 rows                            | ~1.3×                                                                                                            |
| Clear rows                                   | ~2.4×                                                                                                            |
| Sortable table initial mount (5k / 10k rows) | ~2.0×                                                                                                            |
| Per-row JavaScript memory (heap snapshot)    | notably higher; earlier snapshots showed extra `onClick`/`getHandler` closures and owner/context objects per row |

Updates, selection, swaps, removal, and sorting are already near parity. The gap is concentrated in **creating and disposing** many component instances.

### Targets

| Workload                            | Target vs Solid                |
| ----------------------------------- | ------------------------------ |
| Create, replace, append, 10k create | ≤ 1.25×                        |
| Table initial mount                 | ≤ 1.3×                         |
| Clear                               | ≤ 1.5×                         |
| Per-row JS memory                   | ≤ 1.5×                         |
| Update, select, swap, remove, sort  | no regression                  |
| Kernel benchmark guard              | still ≤ 2× Preact on every row |

Targets are goals, not requirements to force: if a target can't be reached without breaking a constraint, report the honest result.

## 3. Hypotheses to Test (not conclusions)

- **Runtime template interpretation:** each instance walks a template plan and allocates scope objects and slot-operation closures. Solid's compiler instead emits direct DOM code (`cloneNode`, `firstChild`/`nextSibling` walks, direct insert and effect calls).
- **Per-binding allocation:** each dynamic binding may allocate an effect node, closure, and owner link, even when the binding is static after first evaluation.
- **Event records:** extra per-handler `getHandler` and wrapper closures per row; delegation could store the handler directly on the element.
- **Owner per row:** owners and contexts allocated even when a row registers no cleanup.
- **Disposal cost:** per-row owner disposal and individual node removal dominate clear and replace.

---

## 4. Constraints to Respect

- **SSR seam:** `compiler.md` and `ssr.md` reserve a host-neutral template plan for future server rendering. If you propose direct DOM code generation, the design must show how SSR remains possible (for example, separate client and server outputs from the same analysis), without implementing SSR.
- **Optimization parity:** compiler output with `optimization: 'none'` and `'safe'` must keep identical behavior; all compiler fixtures must pass in both modes.
- **Dev/production parity:** production output must behave identically to development output, minus diagnostics.
- **Ownership, scheduling, and error semantics** in `reactivity.md`, `scheduling.md`, and `ownership.md` are unchanged.

### Size budgets

Core is at about 4,049 / 4,096 bytes and core + dom at about 10,198 / 10,240. Performance work may need more room. You may **propose** a budget increase, but only with:

- the exact byte cost of each change,
- its measured performance gain,
- and the alternative considered.

I decide on any budget change. Also measure **application bundle size** (the gallery and dashboard builds), since generated code per template may grow even if the runtime shrinks.
