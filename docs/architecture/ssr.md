# Server rendering, streaming, and hydration

**Status:** Phase 2 design; designed now, built later. SSR and hydration are outside v0.1. This document reserves internal seams in the Phase 1 kernel and the provisional Phase 4 renderer; it adds no v0.1 exports.

## Goals and non-goals

The same component functions should produce server HTML and hydrate into the client owner tree without rerunning components on later signal writes. Signals, computed values, context lookup, error routing, and disposal follow [reactivity.md](./reactivity.md) and [ownership.md](./ownership.md). Server output must escape untrusted content, stream independently resolved Suspense boundaries, serialize only intentional data, and reuse matching DOM nodes on the client.

This design does not include a router, server components, automatic request data cache, automatic event replay, cross-request global-state isolation for user module variables, or SSR implementation in v0.1. Server effects and lifecycle callbacks must not perform browser work.

## Proposed later surface and internal seam

Candidate `@benosjs/server` exports are `renderToString(app, options)` returning `Promise<string>` and `renderToStream(app, options)` returning a Web `ReadableStream<Uint8Array>` plus an abort handle. Candidate `@benosjs/dom` export `hydrate(app, host, options)` returns an idempotent disposer. These signatures, adapter choices, and import paths are provisional until the SSR implementation phase. A shared request identifier must be passed to both server and client for multiple roots on one page.

The compiler should emit one logical template/binding description that either a DOM host or HTML host can execute. Its internal host contract needs operations for element/text creation, attributes, child ranges, event descriptors, branch anchors, and owner/binding registration. The server host serializes these operations; the browser host creates or claims nodes. This is an **internal** interface until a second renderer validates it, matching [ownership.md](./ownership.md). The compiler must not rely on browser globals while evaluating a server component. A server-mode flag on the root/scheduler suppresses user effects, DOM render effects, and `onMount` jobs; computed reads and component setup still run synchronously. The server host evaluates bindings once for HTML and never subscribes a DOM effect. This is a scheduler policy attached to the render root, not a new public reactive primitive.

## Request and owner lifetime

1. Each request gets one detached renderer root with a request-local render context, marker namespace, resource registry, and abort signal. Components and provider children get the same logical owner parentage as on the client. Context travels through that tree, including portal-like logical children; it is never taken from the DOM location. A public `createRoot` made during request execution stays detached for context and parentage, but inherits server mode and is tracked for request-end disposal so it cannot leave a live effect graph behind.
2. Component setup and computed reads run synchronously under their owners. A server component may create signals and computeds, but user `effect`, DOM render effects, and `onMount` callbacks remain dormant and are disposed with the root. `onCleanup` runs when a branch or request root disposes. A server `onMount` registration is accepted in a renderer-associated component owner but never executes.
3. A streaming continuation stores an explicit owner token and request generation. On resolution it reenters that owner only for its synchronous render work, restoring the prior owner in `finally`; it never keeps a global owner current across `await`. Abort or client disconnect aborts owned resources, cancels outstanding boundary work, closes the stream, and disposes the root. A finished stream disposes the root after all output is emitted.
4. User module-level mutable signals are outside the request root and can leak state across requests. Server rendering must reject or warn on writes to an ownerless signal during a request in development, and documentation must require per-request state creation. A production isolation rule needs validation before SSR ships; this design does not silently claim arbitrary module state is isolated.

The server-mode effect rule corrects the Phase 1 scheduler's earlier implication that only DOM effects and mount jobs were suppressed. Running a user effect during SSR could cause side effects or read DOM that does not exist. [Scheduling](./scheduling.md) and [ownership](./ownership.md) now state the broader suppression and disposal rule.

## HTML, markers, and serialization

The server escapes text and attribute values by context; raw HTML requires an explicit trusted API designed separately. URL and style handling must share the DOM renderer's security rules. A versioned, root-namespaced marker grammar identifies dynamic text and branch range boundaries (for example, comment anchors with numeric IDs) and element claims (reserved data attributes). IDs derive from deterministic template position and branch/key path, never from `Math.random()` or server-only timing. The exact byte grammar must be frozen with compiler and hydration tests before release; marker compatibility is hard to reverse. Marker placement must be tested against HTML parser behavior in tables, selects, SVG, and malformed input; when a comment would move, the compiler chooses a safe element marker or rejects that template for hydration.

Resource data is **opt-in** for serialization. An SSR-enabled resource must declare a stable resource ID and an explicit serializer/deserializer or safe projection; only the projected JSON-compatible value and status needed to reproduce the committed HTML are emitted. Private fields in a fetched object must not be copied merely because they exist. A resource without this contract leaves its Suspense boundary in fallback for server HTML and fetches on the client; its client-only pending token does not hold the server stream open. Reading it outside a Suspense boundary during server rendering is an explicit error. Payloads are length bounded, versioned, scoped to the request/root and resource ID, and escaped for safe embedding in HTML (including `<`, `&`, and script-closing sequences). Arbitrary classes, functions, symbols, and cyclic objects are rejected unless a codec handles them. Error objects are not serialized with stacks or raw messages by default; a boundary fallback and a public error code can be sent instead.

The client loads a serialized-resource snapshot registry **before** executing hydrate setup. As each resource is created during setup, it claims a validated snapshot so initial `read()` calls and source keys match the server state and do not automatically refetch. A resource that lacks a matching payload remains pending and uses its fallback. The client validates payload version, root namespace, resource ID, and source key; invalid payloads are ignored and the relevant boundary client-renders or refetches. The eventual resource API in [async.md](./async.md) therefore needs an optional SSR serialization contract, while its `value` and discriminated `state` signals remain unchanged.

## Streaming algorithm

The shell contains immediately available HTML and Suspense fallbacks with stable boundary markers. Each boundary has a request-local token and an owner scope. Resources that complete later produce an HTML fragment plus any allowed serialized payload. The stream emits a versioned patch envelope for that boundary and supports two explicit delivery modes. In **strict mode**, a small external client runtime applies envelopes only after it loads and confirms that matching root and boundary markers remain live. Until then, streamed fragments may arrive in the document but their content is **not revealed**; slow or blocked runtime loading delays visible streamed content. In **nonce mode**, an inline patch script with the application's CSP nonce accompanies each envelope and can apply it as it arrives, before the external runtime loads. The nonce must come from trusted server configuration, never from resource data, and the same marker and payload validation applies. Strict mode is the default; nonce mode is opt-in. Ordered transport writes are preserved, but independent sibling boundaries may resolve out of order. A parent patch never invalidates a child patch already applied: nested boundaries are represented within their parent's fragment and have scoped IDs. If a parent is aborted or replaced, queued child patches are discarded.

The stream respects writer backpressure; resolved fragments are buffered within a configured byte budget and can pause upstream output. A boundary that errors after the shell either emits its nearest error-boundary fallback as a safe patch or terminates the stream if no boundary can handle it. Internal error detail goes to server logging, not HTML. Aborting before shell emits no partial success response; aborting after shell closes or errors the stream and disposes the request root. Streaming patch envelopes and resource payload versioning are protocol commitments and need compatibility tests.

## Hydration and event attachment

1. `hydrate` checks the marker protocol/root namespace, creates a client root, loads serialized resource snapshots, and runs components once to recreate owners and binding descriptors. It claims existing DOM nodes by marker and structural position; it does not create duplicate nodes on a successful match.
2. During claim, render bindings compare or record current values but do not mutate the DOM until the matching range is established. Event descriptors attach delegated listeners at the root and native listeners at their elements; both use automatic `batch` from [scheduling.md](./scheduling.md). Refs receive their non-null claimed element once. User effects remain gated until the matching region is claimed and event attachment is complete. `onMount` then runs after that region is in the live document.
3. The shell and each arriving streamed patch may hydrate independently. A fallback can be interactive while its parent boundary is pending. When a patch replaces it, its owner and listeners dispose before the new region is claimed; the replacement's owner/effects/mount jobs begin after insertion. If a patch arrives before the client runtime starts, the runtime discovers its envelope during startup. Events before a region is hydrated are not replayed; browser default behavior still applies. This must be stated in user docs.
4. A mismatch produces a development diagnostic with root/marker/component path and expected versus actual node kind. Recovery disposes the affected tentative owner and client-renders the **smallest complete marked boundary**; if the root markers themselves are invalid, it replaces the root. Production uses the same recovery without verbose details. It never silently patches an arbitrary half-claimed range. Form controls with user input during hydration require a specific preservation rule: keep current `value`/`checked` unless a controlled binding explicitly overwrites them after claim.
5. A hydration failure does not leak tentative owners, listeners, or subscriptions. Successful hydration reuses node identity and installs the ordinary render-first scheduler. Subsequent signal writes follow the same v0.1 timing; SSR adds no microtask delay to writes.

## Trade-offs and prior art

[Solid hydration](https://docs.solidjs.com/reference/rendering/hydrate) uses markers to reuse server DOM and [Solid streaming](https://docs.solidjs.com/reference/rendering/render-to-stream) sends async fragments after a shell. [React streaming](https://react.dev/reference/react-dom/server/renderToPipeableStream) and [hydration](https://react.dev/reference/react-dom/client/hydrateRoot) show the importance of matching server/client trees and explicit mismatch handling. Benos chooses opt-in resource serialization and two patch delivery modes. Strict mode avoids inline executable scripts but can delay visible streamed content; nonce mode reveals patches promptly where CSP allows trusted inline scripts. Both add compiler and protocol work. The internal host interface should remain unpublished until these paths prove it general enough.

## Test plan before implementation

1. Same component output and owner/context behavior on server and client; no user effect, DOM effect, or `onMount` executes on server; cleanups run on completion and abort.
2. Safe escaping of text, attributes, JSON payloads, and error representations; no unintended fetched fields appear in HTML.
3. Deterministic marker IDs across requests and under branches/keys; parser round trips for table/select/SVG; multiple roots do not collide.
4. Streaming shell then sibling and nested boundaries in different resolution orders, backpressure, abort, error after shell, and late patch rejection. Delay loading the external runtime to prove strict mode delays reveal; verify nonce mode applies patches before that runtime loads and rejects a missing/wrong nonce under CSP.
5. Hydration preserves node identity, installs delegated/native events exactly once, batches event writes, calls refs with elements only, and defers effects/mounts until claim/insertion.
6. Missing/invalid payload, source-key mismatch, text/attribute/structural mismatch, recovery within one boundary, and root fallback without leaked owners.
7. Client events before hydration follow documented browser behavior; form input entered before hydration is preserved until a controlled binding intentionally updates it.

## Hard-to-reverse decisions

Marker grammar and versioning, payload format and opt-in policy, mismatch recovery scope, event replay policy, effect suppression on the server, and the **strict versus CSP-nonce patch delivery modes and their reveal timing** are protocol or user-visible choices. They are hard to reverse and must be frozen with paired server/client fixtures and browser tests before any SSR release. The Phase 1 graph primitives remain synchronous and DOM-free.
