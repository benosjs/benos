# Ten principal build risks

**Status:** Phase 2 assessment; designed now, built later where the risk concerns async or SSR. The v0.1 mitigations are planning and validation gates, not added implementation scope.

Likelihood and impact are qualitative estimates for reaching a credible v0.1 and preserving a path to later async/SSR work. “High impact” means the issue could force a public API change, invalidate the flagship dashboard, or make the package unsafe to adopt. Reassess these estimates at each phase checkpoint.

## Phase gates

1. **Before Phase 3:** resolve contradictory graph, scheduler, and owner rules in the three Phase 1 documents; preserve the server/staging hooks without adding public async or SSR APIs.
2. **Before Phase 4:** core tests and coverage establish the exact timing, cleanup, error, cycle, and memory contracts; packed core imports work from an external fixture.
3. **Before v0.1 approval:** require the type-level sketch of the flagship route/query/form/mutation/cache integration, then use compiler/renderer fixtures, dashboard behavior, production build, package compatibility, diagnostics, and documented trade-offs to support the claims. The sketch is design evidence, not authorization to build those modules. Async and SSR remain unimplemented even if their designs are complete.

## Phase 5b residual performance gap

The focused production trace round did not meet the requested 1.3× Solid targets for create (1.57×), replace (1.68×), or append (1.33×), nor the 2× clear target (2.46×). The leading-row removal gap was reduced to 1.12×. Heap snapshots after 1,000-row creation showed approximately 5.93 MB of additional V8 heap for Benos versus 1.87 MB for Solid; JavaScript snapshot self-size grew 3.87 MB versus 0.67 MB. The remaining evidence points to per-row ownership and event-handler closures, descriptor allocation, and DOM insertion. These numbers are recorded as a Phase 5b limitation and are not a reason to raise the 10 KB core-plus-DOM budget. Phase 5c proceeds with this gap documented; later performance work must preserve the public API, production budget, and scheduler semantics.

This list deliberately treats differentiation and adoption as risks to the engineering outcome; performance alone cannot settle whether the framework is useful.
