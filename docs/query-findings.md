# Query findings from a TanStack Query user's perspective

The dashboard's project pages now read through `@benosjs/query`. Both route loaders use `query.load`, and the detail page renames a project and stars it optimistically. These notes record where the workflow differs from React with TanStack Query, and classify each item as a `0.5 fix` (done in this track), a `0.5 item` (for the forms/flagship track or needing approval), a `later` item, or an `accepted trade-off`.

| Finding                                                    | What felt different or confusing                                                                                                                                                                                                                                                                                                                                                                                       | Disposition                                                                                                                                                                                                                                                                                                                                                     |
| ---------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `<Show>` recreates its function child on every data change | The detail page first used `<Show when={project()}>{(current) => …}</Show>`. Every cache write or refetch is a new object, so `<Show>` called its child again and recreated the editor. The rename status ("Saved.") and the star error disappeared the moment they were set, because their mutation handles were new. React keeps component state across prop changes unless a `key` changes, so this was surprising. | `0.5 fix` — approved as option 2 and fixed in Q5a: `<Show>` keeps its branch while `when` stays present and the accessor tracks the latest value, which is what [components.md](./architecture/components.md) already specified. The dashboard uses the plain `<Show when={project()}>{(current) => …}</Show>` form again. See [q-q5a](./checkpoints/q-q5a.md). |
| Editable copies are captured once                          | `signal(props.project().name)` seeds the rename field from the data once. A later refetch does not update the field, and a different record would need a new editor. TanStack Form handles this with changing default values.                                                                                                                                                                                          | `fixed in 0.5` — the forms track's `formModel` follows the committed record: pristine fields follow refetches, dirty fields are kept, and a different record resets at commit. The dashboard editor uses it since forms F5 ([forms-findings.md](./forms-findings.md)).                                                                                          |
| Route data is an entry, not a value                        | `match.data().value()` replaces `useLoaderData()` or `useSuspenseQuery(...).data`. The extra call is what makes route data live, so mutations update it in place, but the double call reads oddly at first.                                                                                                                                                                                                            | `accepted trade-off` — documented in [query.md](./architecture/query.md#router-loaders-share-identity-with-queries); a page can wrap it once in a local accessor, as the dashboard does.                                                                                                                                                                        |
| Argument-free queries and `void`                           | The design showed `fetch: (_: void, { signal }) => …`, which the repository's `no-invalid-void-type` lint rule rejects, so app code hit a lint error immediately. An unannotated parameter, `fetch: (_, { signal }) => …`, infers the same argument-free query.                                                                                                                                                        | `0.5 fix` — query.md and the dashboard now use the unannotated form, and a type test covers it.                                                                                                                                                                                                                                                                 |
| Mutations never throw                                      | `void rename.run(input)` and reading `rename.state()` replaces `mutateAsync` with `try/catch`. There is no `onError` callback; validation errors such as "Names need at least two characters." come from `state()`.                                                                                                                                                                                                    | `accepted trade-off` — this is the design's no-unhandled-rejection rule. The editor needs no `try/catch` and no error signal of its own.                                                                                                                                                                                                                        |
| Optimistic updates are declared, rollback is automatic     | Starring touches the detail entry and the cached list. `optimistic` lists both writes and the library rolls them back when the server refuses a paused project. There is no `onMutate`/`onError`/`onSettled` snapshot code, but the list updater (`withStar`) is still written by hand, as in TanStack.                                                                                                                | `accepted trade-off` — less code than TanStack's optimistic recipe; a typed list helper could come later if more apps need it.                                                                                                                                                                                                                                  |
| HTTP errors need a `status`                                | The transient-only retry policy reads a numeric `status` from the error. A plain `fetch` wrapper must attach it; TanStack retries every error, so it never needs to know. In return, the 409 and 422 errors here appear immediately instead of after backoff.                                                                                                                                                          | `later` — consider a tree-shakable `httpError(response)` helper in the query guide or API. Not needed for the dashboard, whose in-memory API attaches `status` itself.                                                                                                                                                                                          |
| Abandoned navigations cancel their request                 | Clicking away while a project is loading aborts that loader's request when nothing else wants it, so the next visit fetches again. TanStack also cancels a query whose `queryFn` consumes the `AbortSignal` when it is no longer used. A browser test first failed because it clicked away before the detail page committed.                                                                                           | `accepted trade-off` — it is the designed last-joiner rule; the test now waits for the detail page.                                                                                                                                                                                                                                                             |
| Cache visibility                                           | Proving a cache hit meant adding a request log to the demo API. TanStack Devtools shows entries, staleness, and observers directly.                                                                                                                                                                                                                                                                                    | `later` — part of the devtools roadmap item.                                                                                                                                                                                                                                                                                                                    |
| Loaders and non-default caches                             | The dashboard uses the default cache, so loaders needed nothing. An app with its own cache must pass it to `load` explicitly, because loaders run under detached roots.                                                                                                                                                                                                                                                | `accepted trade-off` — documented in [Q4 implementation notes](./architecture/query.md#q4-implementation-notes).                                                                                                                                                                                                                                                |

## Dashboard validation

The dashboard is type-checked and built in CI. Its browser tests now also cover cache revisits without new requests (via the demo API's request log), a rename that updates the detail view and the cached list, a rejected short name, an optimistic star that persists, and an optimistic star that rolls back when the server refuses it. They run in Chromium, Firefox, and WebKit.
