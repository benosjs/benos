You are the lead architect for the next Benos track (`@benosjs/*`, currently v0.5.0): **server rendering and hydration**. The same component functions produce HTML on the server and then hydrate into a live client owner tree, reusing the server's DOM nodes. Streaming follows in its own track and builds on the marker and payload protocols this track freezes.

Build in phases with review checkpoints: design first, then implementation, with tests at every step. Push back when an idea is technically weak.

## 2. Context You Must Read First

- `docs/architecture/ssr.md`: the Phase 2 SSR design (request and owner lifetime, markers, opt-in serialization, streaming, hydration, mismatch recovery, deterministic IDs). This track implements its string-rendering and hydration parts and freezes their protocols.
- `docs/architecture/compiler.md` and `renderer.md`: the host-neutral template plan, the safe direct template path, and the internal host contract. The server host consumes the same plan.
- `docs/architecture/scheduling.md` and `ownership.md`: the server-mode suppression of user effects, DOM render effects, and `onMount`, and request-root disposal.
- `docs/architecture/async.md` ("SSR compatibility check"), `query.md` (rule 5, request-local cache), `router.md` ("Lazy routes and SSR seam"), and `forms.md` ("Ids"): the hooks each module already reserved for this track.
- `docs/architecture/flagship-integration.md`: the editor that must render on the server and hydrate unchanged.

### Constraints carried over

1. **Components run once.** Hydration runs each component's setup once to recreate owners and bindings; it never reruns components on later writes, and SSR adds no microtask delay to writes after hydration.
2. **Opt-in serialization only.** Resources and queries are serialized only through their declared `ssr` codec. Private fields of fetched objects never reach HTML. Data without a codec leaves its Suspense fallback in server HTML and loads on the client.
3. **Request isolation.** Every request gets its own root, ID namespace, resource registry, query cache, and abort signal. Module-level mutable state is not claimed to be isolated; development warns on ownerless signal writes during a request.
4. **Safe output.** Text and attributes are escaped by context; URL and style rules match the DOM renderer; payloads escape `<`, `&`, and script-closing sequences. Error details go to server logs, not HTML.
5. **No hidden behavior.** No automatic event replay before hydration, and no automatic data fetching on the server beyond what component setup and route loaders already start.

## 3. Goals for the SSR track

### `@benosjs/server` (new package)

- `renderToString(app, options)` returning a promise of the HTML and the serialized payload, with `signal` for abort and `rootId` for multiple roots per page. It waits for opted-in resources and queries, leaves fallbacks for the rest, and disposes the request root when done or aborted.
- A server host that serializes the compiler's existing host-neutral template plan (and the safe direct path's static skeleton). No second code generation path.
- Request-scoped `createUniqueId` behind the existing signature, derived from the root namespace, owner path, and call ordinal.

### `@benosjs/dom/hydrate` (new entry)

- `hydrate(app, host, options)` returning an idempotent disposer: claims server nodes by marker and position, attaches delegated and native events once, gates effects and `onMount` until claim, hands refs their claimed elements, and loads payload snapshots before setup.
- Mismatch handling: a development diagnostic with root, marker, and component path; recovery that client-renders the smallest complete marked boundary (or the root); no leaked owners, listeners, or subscriptions. User input in form controls is preserved until a controlled binding intentionally updates it.

### Module integration

- `@benosjs/async`: implement the reserved `resource` `ssr` codec (`id`, `key`, `serialize`, `deserialize`).
- `@benosjs/query`: a request-local cache on the server, opted-in serialization, and client cache seeding from the payload.
- `@benosjs/router`: request-local server history from the request URL, loaders awaited before rendering, and redirects and not-found exposed as status and `Location` for the response.
- `@benosjs/forms`: field IDs that are stable across server rendering and hydration.

### Tooling and validation

- `@benosjs/vite`: server and client builds using Vite's SSR mode, with the compiler running in server mode where needed.
- The dashboard example rendered on the server through a plain `(request: Request) => Promise<Response>` handler, then hydrated.

### Not in this track

Streaming (`renderToStream`, strict and CSP-nonce patch delivery, out-of-order Suspense patches), event replay before hydration, server components and server actions, a `create-benos --ssr` template, and `<head>`/meta management (the user's HTML template provides the head). A string-concatenation fast path for the server host is a possible later optimization, not part of 0.6.0.

### S2 — Server renderer

### S3 — Hydration

The `@benosjs/dom/hydrate` entry and the approved DOM claim seams. Tests in Chromium, Firefox, and WebKit: node identity preserved; delegated and native events installed exactly once with batched writes; refs receive claimed elements; effects and `onMount` wait for claim; payload snapshots prevent a refetch; missing or invalid payload, source-key mismatch, and text, attribute, and structural mismatches recover within one boundary, with a root fallback and no leaked owners; form input entered before hydration is preserved; events before hydration follow documented browser behavior.

### S4 — Data and routing integration

The `resource` codec, the query request cache and payload, router server history, loaders, status and redirects, and hydration-stable form IDs. Tests: a route loader's query data renders on the server and is reused on the client without a refetch; a redirect and a not-found route produce the right status and headers; an aborted request cancels loaders and fetches; two concurrent requests never share cache entries or IDs; the flagship editor renders on the server and hydrates with identical behavior to client rendering.

### S5 — Tooling and validation app
